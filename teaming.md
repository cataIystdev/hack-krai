# Teaming Guide

## Назначение

Этот файл описывает, как должны синхронизироваться бэкендер и фронтендер, чтобы:

- не блокировать друг друга;
- быстро собрать demo-first сценарий;
- после демо без хаоса перейти в MVP;
- не плодить лишние моки и переделки.

## Главный принцип

Работа идет не по схеме:

- сначала весь бэкенд;
- потом весь фронтенд.

И не по схеме:

- `B0 -> F0 -> B1 -> F1`.

Правильная схема такая:

1. Бэкенд чуть опережает фронтенд.
2. Бэкенд отдает стабильный кусок контракта.
3. Фронтенд под этот кусок собирает экран.
4. Пока фронтенд собирает экран, бэкенд уже идет в следующий кусок.

То есть работа идет волной, а не очередью.

---

## Модель взаимодействия

## Что делает бэкенд

Бэкенд отвечает за:

1. стабильные контракты;
2. shape payload;
3. seed/demo data;
4. реальные или mock-safe endpoint’ы;
5. backward-compatible эволюцию API.

## Что делает фронтенд

Фронтенд отвечает за:

1. сборку финального UI под переданный контракт;
2. корректное использование handed-off payload;
3. отделение mock data layer от UI;
4. быструю обратную связь по неудобным полям/форматам.

## Что нельзя делать никому

1. Ломать shape payload без предупреждения.
2. Менять имена ключей “по ходу” без handoff.
3. Параллельно выдумывать разные модели одной и той же сущности.
4. Тащить временный хардкод в боевые экраны без пометки.

---

## Когда пинговаться

Пинговаться нужно не “когда вспомнили”, а в фиксированные моменты.

## 1. Пинг перед стартом фазы

Короткий пинг нужен, когда:

- стартует новая backend-фаза;
- стартует новый фронтовый экран;
- есть выбор между mock и real implementation.

Формат:

1. что начинаем;
2. какой целевой экран/endpoint;
3. что считаем минимальной готовностью;
4. что может заблокировать.

## 2. Пинг на handoff

Это главный пинг.

Бэкенд обязан пинговать фронтенд, когда:

1. endpoint уже существует;
2. payload зафиксирован;
3. есть 1-2 рабочих JSON examples;
4. понятно, mock там пока или real.

Без этого фронт не должен “догадываться” о контракте.

## 3. Пинг на change request

Если фронт видит, что:

- payload неудобный;
- не хватает поля;
- не хватает статуса/флага;
- экран из-за API получается костыльным,

он пингует бэк не общими словами, а в формате:

1. какой экран;
2. какой endpoint;
3. какого поля не хватает;
4. почему без этого начинается костыль.

## 4. Пинг на freeze

Перед съемкой или перед важной сборкой делается freeze-пинг:

1. какие endpoint’ы считаются замороженными;
2. какие экраны снимаются;
3. какие данные моковые;
4. что нельзя менять до конца съемочного этапа.

---

## Что считается нормальным handoff от бэкенда

Хороший handoff от бэкенда содержит:

1. название endpoint’а;
2. метод;
3. пример запроса;
4. пример успешного ответа;
5. список возможных состояний/ошибок;
6. пометку:
   - `real`
   - `mock-safe`
   - `temporary demo`.

Минимальный шаблон:

```md
Endpoint: POST /api/v1/profile/voice
Status: mock-safe, shape frozen
Used by: voice screen, vibe passport
Request: multipart/form-data, field audio
Response example: ...
Known limitations: deterministic mock axes in demo mode
Safe for frontend: yes
```

---

## Что считается нормальной обратной связью от фронтенда

Хорошая обратная связь от фронта:

1. привязана к конкретному экрану;
2. привязана к конкретному endpoint’у;
3. объясняет, почему текущий shape неудобен;
4. предлагает изменение минимального масштаба.

Плохая обратная связь:

- “что-то payload неудобный”
- “давай как-нибудь по-другому”

Хорошая:

- “для vibe passport нужен `summary`, `axes`, `tags`, и еще один `title`, иначе приходится генерить заголовок на фронте и он уедет от продукта”.

## Порядок работы на demo-first

## Шаг 1. Backend Phase 0

Бэкенд делает:

1. freeze контрактов demo-flow;
2. фиксирует JSON examples.

После этого пинг фронтенду:

- можно начинать shell и product routes;
- можно начинать voice/passport/map/detail screens как макеты на стабильных shapes.

## Шаг 2. Frontend F1 + F2 + F3

Фронтенд делает параллельно:

1. product shell;
2. data layer;
3. стартовый экран.

Бэкенд в это время идет дальше.

## Шаг 3. Backend Phase 1 + 2

Бэкенд делает:

1. demo data foundation;
2. `POST /profile/voice`.

Пинг фронту:

- можно собирать `/vibe/voice`;
- можно собирать `/vibe/result`.

## Шаг 4. Frontend F4 + F5

Фронтенд делает:

1. voice screen;
2. AI thinking state;
3. vibe passport.

Бэкенд в это время идет в recommendations/map.

## Шаг 5. Backend Phase 3 + 4

Бэкенд делает:

1. finalize/recommendations;
2. `GET /map/locations`.

Пинг фронту:

- можно собирать карту рекомендаций.

## Шаг 6. Frontend F6

Фронтенд делает:

1. карту;
2. recommendation overlays;
3. главный wow-screen.

## Шаг 7. Backend Phase 5

Бэкенд полирует:

1. location detail;
2. media/detail payload.

Пинг фронту:

- можно собирать финальный detail screen.

## Шаг 8. Frontend F7

Фронтенд делает:

1. location detail / 3D preview shell;
2. финальный кадр для скринкаста;
3. третий скриншот.

## Шаг 9. Freeze перед съемкой

Оба делают freeze:

1. список экранов для съемки;
2. список endpoint’ов для съемки;
3. что real;
4. что временно mock;
5. что нельзя трогать до конца захвата.

---

## Порядок работы после демо

Сразу после demo-first:

1. backend идет в `Phase 5.5`;
2. frontend идет в `Phase F7.5`.

То есть сначала:

- закрываются опасные code-review замечания;
- стабилизируется техническая база;
- только потом команда идет глубже в MVP.

Дальше волна продолжается:

1. Backend 6 -> Frontend 8
2. Backend 7 -> Frontend 11
3. Backend 8 -> Frontend 12
4. Backend 9 -> Frontend 9
5. Потом уже host/booking/live/story и т.д.

---

## Что делать, если бэкенд не готов

Если бэкенд еще не готов, фронтенд может идти дальше только если:

1. контракт уже frozen;
2. есть payload example;
3. есть пометка, что data source временно mock.

Если этого нет, фронтенд не должен сам изобретать модель сущности.

---

## Что делать, если фронтенд не успевает

Если фронтенд не успевает:

1. бэкенд не тормозит следующие endpoint’ы;
2. бэкенд подготавливает следующий handoff;
3. фронтенд добирает экраны по уже стабилизированным кускам.

То есть отставание фронта не должно останавливать backend lane.

---

## Что считается блокером

Блокер — это только то, без чего следующая работа реально невозможна.

Примеры настоящих блокеров:

1. нет shape payload;
2. неясно, какие поля обязательны;
3. endpoint будет переименован или переписан;
4. невозможно понять, mock это или real.

Не блокер:

1. endpoint еще не идеален;
2. внутри пока mock mode;
3. часть enrichment будет добавлена позже, если базовый shape уже frozen.

---

## Формат короткого ежедневного пинга

Каждый участник пишет коротко:

1. что закончил;
2. что сейчас делает;
3. что отдает другому;
4. что блокирует.

Шаблон:

```md
Готово:
- ...

В работе:
- ...

Handoff:
- endpoint / screen ...

Блокеры:
- ...
```

---

## Формат freeze-пинга перед записью

```md
Freeze window:
- start screen
- voice
- passport
- map
- location detail

Frozen backend:
- POST /profile/voice
- POST /profile/finalize
- GET /map/locations
- GET /locations/{id}

Mocks allowed:
- demo recommendations
- fake 3D preview

Do not change until recording is done:
- payload shape
- button labels
- screen order
```

---

## Критерий хорошей командной работы

Команда работает правильно, если:

1. фронт почти никогда не ждет “пока бэк когда-нибудь закончит все”;
2. бэк почти никогда не слышит “мы сами придумали payload, потом подгони”;
3. demo и MVP используют одни и те же сущности и экраны;
4. mock-режимы не ломают будущую архитектуру.
